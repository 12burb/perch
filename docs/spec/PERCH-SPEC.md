# 0. MISSION

Perch is a self-hosted, open-source agentic workspace in one TypeScript monorepo:
- an OpenCode-simple IDE (project → editor → terminal → agent session → diff review),
- a Slack-shaped team chat where bots are members, can be @tagged by humans and by other bots, and work together in threads,
- a bot forge (no-code form → YAML spec → TypeScript handler → external Bot API),
- connections to GitHub, Vercel, Supabase, Clerk, and any MCP server or OAuth service, with tokens that never leave the instance,
- a preview browser with a click-to-source inspector for dev servers running in the workspace,
- Plane-shaped work tracking (work items, cycles, board, intake) and an approval inbox,
- a gateway that uses any API key, local model (Ollama), or vendor-permitted subscription.
The wedge, the loop nobody ships end to end: a task appears in chat → an agent takes it in its own git worktree, server-side → the human watches a preview from a phone → approves the diff → it becomes a PR → the channel sees the outcome, with cost and trace recorded. Be #1 at that loop; be good enough and interoperable everywhere else (ACP, MCP, AGENTS.md, Agent Skills, devcontainer.json, OpenAPI). Working name: Perch. License: AGPL-3.0 for apps/*; MIT for packages/bot-sdk, packages/ui, packages/events, packages/api-client, connectors/, templates/.

# 1. GROUND RULES (never break these)

1. TypeScript end to end, runtime Bun. Bun workspaces + Turborepo, Biome, strict TS with noUncheckedIndexedAccess, Zod at every boundary. No other language in this repo; Python exists only as third-party agent runtimes inside the runner image. No `any`.
2. TASKS.md (§11) is the queue. Take the first unchecked task whose prerequisites are checked. One task per branch (task/<id>-<slug>), one branch per PR. Never batch tasks. Never start a task whose prerequisites are unmerged.
3. Resolve exact package names and versions from official docs before adding any dependency (task 0.3) and pin them. Never guess a package name. Nothing in this spec is a version pin.
4. Run every Phase 0 spike (§9.3) as its own PR; record each outcome in DECISIONS.md before building on it; if a spike fails, take the listed fallback.
5. Implement §7 contracts exactly: paths, envelopes, event names, error shapes. Any deviation = an ADR in DECISIONS.md + a "Spec deviations" note in the PR.
6. Security invariants: no connection token, API key, or subscription credential ever reaches an engine, a bot, a model context, a log line, or the client — vault in, gateway out. apps/api never mounts the Docker socket; only the supervisor does. Runners speak only the §7.6 protocol; a local runner refuses requests for users other than its owner unless a grant is attached. Personal subscription credentials are user-scoped and never proxied; anything shared runs on API keys or local models. Perch never forwards a caller's bearer token upstream; each connection uses its own delegated token.
7. Every screen follows the §4 shell; every long list is virtualized; every flow works at a 390 px viewport; every component has ARIA roles and labels.
8. Definition of done: code + tests + changeset + docs updated + ADR for any choice not in this spec + `bun run check` green + the relevant Playwright spec green + the task's acceptance criterion demonstrated in the PR description. Never skip, weaken, or disable a test to get green.
9. Do not ask the human questions. Choose the sane default, record it in DECISIONS.md, keep going. If the spec is wrong or impossible, build the closest correct thing and write the ADR.
10. Do not add infrastructure beyond §3.1 (no Redis, queues, object stores, extra services) without an ADR.
11. Per-task workflow: branch → mark [~] in TASKS.md with branch name → re-read the spec sections the task names → write the acceptance test first when testable → implement → `bun run check` + Playwright → update docs → `bun run changeset` → conventional commit with DCO sign-off (`git commit -s`) → open PR with the template (what/why, spec sections, acceptance evidence, 390 px + 1440 px screenshots for UI, spec deviations, ADRs) → mark [x] with PR link in the same PR → next task.

# 3. ARCHITECTURE

3.1 Services (docker-compose, four containers by default): caddy (TLS, reverse proxy, WS passthrough, wildcard cert for previews via DNS challenge); api (one Bun process: HTTP+WS, auth, workspaces, chat, bots, registry, gateway, connections, MCP gateway, preview proxy, Bot API, jobs worker, event bus; serves the built web app); postgres (image pgvector/pgvector:pg16; data, full-text search, vectors, job queue, session events); supervisor (same image as api, entrypoint `supervisor`, owns the Docker socket, creates one runner container per workspace on demand with CPU/memory/pid limits and idle stop). Dynamic: runner (perch/runner image: project volumes, per-user home volumes at /data/homes/<user>, PTY, OpenCode server, ACP agents, Hermes Agent, bot sandboxes, official CLIs claude/codex/gemini/hermes/opencode, git, Bun, Node, Python+uv, Playwright Chromium, tmux). Profiles: local (ollama), tunnel (cloudflared). No Redis, no object store by default: in-process bus, Postgres jobs, in-memory presence and rate limits; files on a local volume or any S3-compatible bucket when PERCH_S3_* is set. PERCH_RUNNER_MODE=docker|shared|inprocess. PERCH_PUBLIC_URL drives every callback, webhook, the CIMD document, and deep links.

3.2 Runners (first-class): hosted (default, supervisor container per workspace), local (`perch runner connect <workspace>` on a laptop/homelab/GPU box opens an outbound WebSocket, registers as one of the owner's environments, hosts that user's sessions, terminals, previews, and CLIs; subscriptions and code stay on the machine), remote (any box you own, same command). The api brokers all runner traffic with short-lived tokens. Environments page shows status, load, cost.

3.3 Engines. Interface (packages/engines):
    interface Engine { id: "acp"|"opencode"|"cli-harness"|"native"|"hermes"|"cli"|"native-code"; capabilities: { code: boolean; tools: boolean; subagents: boolean; streaming: boolean }; createSession(p: { workspaceId; projectId?; userId; model: ModelRef; systemPrompt? }): Promise<Session>; send(sessionId, input: UserTurn, opts?: { mode: "plan"|"build" }): AsyncIterable<EngineEvent>; respondPermission(sessionId, permissionId, answer: "allow"|"always"|"deny"): Promise<void>; cancel(sessionId): Promise<void> }
    type EngineEvent = { type:"text"; delta } | { type:"tool_call"; id; name; args } | { type:"tool_result"; id; output; diff?: FileDiff[] } | { type:"permission"; id; tool; args } | { type:"usage"; input; output; costUsd } | { type:"done" } | { type:"error"; message }
Adapters: acp = THE contract — generic ACP client in the runner; any ACP Registry agent (Claude Code via adapter, Codex, Gemini CLI, Copilot CLI, Goose, OpenCode) becomes an engine; Perch tools reach agents via ACP's MCP passthrough. opencode = OpenCode's extras beyond ACP (`opencode serve` per project, SDK client, plan/build agents, subagents; native provider creds injected for full fidelity). cli-harness (feature flag, off by default) = official CLIs in headless mode under the user's own login: Codex `exec --json`, Claude Code `-p --output-format stream-json`, Gemini CLI; personal scope only. native = AI SDK streamText + Perch tool registry for chat bots. hermes = Hermes Agent runtime for Nest agents (Phase 3). cli = terminal lane, no adapter. native-code = own agentic loop, Phase 5 escape hatch. Pin the OpenCode version in the runner image; the adapter is the only code touching its API. The api persists every EngineEvent to session_events with monotonic seq and republishes on session:<id>.

3.4 Brains (packages/gateway): provider_credentials (scope user|workspace; kind api_key|endpoint|oauth_ref; encrypted), model_profiles (provider, model_id, params, tool_policy, cost_cap, default_for chat|code), catalog seeded from models.dev, per-workspace allow-list. Gateway: OpenAI-compatible POST /v1/chat/completions (streaming), GET /v1/models, POST /v1/embeddings; virtual keys pk_... scoped to workspace/user/bot/runner with budgets; fallback chains; cost logged to usage_events. Fidelity rule: engines get native provider credentials; the gateway serves chat bots and external consumers (Hermes, scripts, Nest cron, OpenCode as a custom provider). Aggregators (OpenRouter, LiteLLM, Cloudflare AI Gateway, OpenCode Zen, Nous Portal proxy) are endpoints you point at, not components. Embeddings are 1024-dim everywhere (ask providers for dimensions:1024; defaults OpenAI text-embedding-3-small@1024 and local mxbai-embed-large).

3.5 Connections (packages/connect). Registration lanes tried in order: pre-registered client (admin-pasted client id/secret) → CIMD (instance publishes https://<PERCH_PUBLIC_URL>/.well-known/oauth-client-metadata.json and uses that URL as client_id; primary path in the MCP auth spec since 2026-07) → DCR (RFC 7591 fallback) → token paste (PAT/API key, always available). MCP OAuth discovery via RFC 9728 → RFC 8414/OIDC metadata → PKCE, using the official MCP SDK client auth; plain OAuth2 providers via Arctic driven by connectors/<provider>/manifest.yaml (auth type, endpoints, scopes, refresh rules, api base, optional mcp url, webhook signature scheme). Vault stores access+refresh tokens; refresh jobs on the Postgres queue; revoke on disconnect. MCP gateway: Perch exposes each connection as a Streamable HTTP MCP server at /mcp/:connectionId (auth: session, api token, or virtual key with a grant); tool allow-lists, permission prompts (tool marked requires_permission returns pending + inbox item, completes on approval), rate limits, audit; upstream calls carry the connection's delegated token, downstream consumers (OpenCode/ACP sessions via injected MCP config, native bots as tools, Bot API tools.call, IDE features) never see raw tokens; runner-local stdio MCP servers are exposed through the same shape; Perch's own MCP server at /mcp/perch (channels.list, messages.search, messages.post, work.create, work.update, sessions.open, connections.call). Scope: connections are personal by default; shared bots use them only when the bot has obo:true and that user invoked it; workspace connections are admin-created with explicit grants (bots, channels, tools) and prefer service identities (GitHub App installation tokens, Vercel team tokens, Supabase project-scoped read-only PATs). Callbacks need a stable HTTPS URL: public domain via Caddy, --profile tunnel (cloudflared), Tailscale Serve/Funnel, or http://localhost:PORT in single-user mode (PERCH_ALLOW_LOOPBACK_REDIRECTS). Inbound webhooks at /hooks/:provider/:id with signature verification → channel cards. Vendor facts (verified Sept 2026): GitHub remote MCP has no DCR → GitHub App (installation tokens, webhooks, check runs) or fine-grained PAT, with a wizard that prefills callback and webhook URLs; Vercel MCP https://mcp.vercel.com OAuth + token fallback; Supabase MCP https://mcp.supabase.com/mcp OAuth 2.1 with DCR, manual app and PAT fallbacks, shared-bot defaults project-scoped read-only; Clerk MCP https://mcp.clerk.com/mcp OAuth (CIMD beta and DCR), secret-key fallback, and Clerk usable as Perch's login via better-auth generic OIDC.

3.6 Credential matrix and lanes. Lane A: API keys and OpenAI-compatible endpoints (Ollama, LM Studio, vLLM, llama.cpp, OpenRouter…) → vault → gateway and native engine injection; user or workspace scope. Lane B: subscription OAuth inside an official/endorsed engine (ChatGPT Plus/Pro, SuperGrok, GitHub Copilot via OpenCode `/connect`; Nous Portal via Hermes) — personal only, lives in the user's home volume, never the vault. Lane C: official CLIs in the hosted terminal or a local runner under the user's own login (Claude Code with a Claude Pro/Max plan, Gemini CLI, Codex CLI) — Perch is a terminal here, not a harness. Anthropic: API key only in engines and bots (Claude subscriptions are not permitted in third-party harnesses; cli-harness for Claude Code stays off until terms are confirmed). Hard rules: a bot visible to more than one person runs on Lane A or a local model; tokens never leave Perch.

Agent eyes: @playwright/mcp in the runner attached to sessions when a preview is open (navigate, accessibility snapshot, screenshot, click, console); Preflight before push: run test/lint/build from project.json, then an agent visual smoke over the configured routes (screenshot each, fail on console errors) → checklist card; configurable warn or block. Security: proxy reaches only the workspace's own runner ports; CSP relaxed only for the injected script on authenticated preview responses; minimum iframe sandbox flags; share links expiring, revocable, audited.

5.7 The agent loop. Work items (state above) arrive from chat (/task, reaction, @dawn do X, "Create work item" on any message), the board, inbound webhooks, or cron. Worktree per task: every session runs in its own git worktree and branch perch/<task-id>; merge queue with rebase, conflict detection, "ask the agent to resolve"; cleanup on close. Race mode: same task on two engines/models side by side; compare diffs, cost, preflight; pick a winner; results feed the eval board. Background by default: sessions keep running when the tab or laptop closes; every state change posts to the task's thread; the phone gets what needs a human. Approval inbox: one queue for permission prompts, preflight results, PRs awaiting review, budget alerts, failed bot runs, chain breakers, intake, mentions; batch approve, snooze, delegate; push to phone; built on interactive blocks. Policy engine (.perch/policy.yaml at workspace and project level): protected branches, denied commands (rm -rf, git push --force, package publishes), path allow/deny lists, secret scanning on every agent diff before commit, per-channel and per-project model allow-lists ("this channel: local models only"), budget ceilings, bot-to-bot rails; violations show as a card with an admin override path; dry-run endpoint. Project env and secrets: encrypted per-project env; import from Vercel and Supabase connectors; injected into runner, previews, sessions; never into a model context; optional Vault/1Password/Infisical/Doppler backends. Repo intelligence: codebase index (symbols + embeddings in pgvector) behind @codebase; semantic search across code, chat, docs; generated repo docs and an AGENTS.md draft for new projects; cross-session project memory. Testing loop: failing tests → bounded auto-fix loop with budget; CI status webhook → agent retry; flaky-test detection. Agent presence: busy/idle, "working on" cards, agent org view, assignment from chat.
